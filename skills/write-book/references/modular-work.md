# Modular work on a volume

Read when a volume is written unit by unit: when the next chapter, a whole part or a whole volume is ordered. A module is one unit of text: a prologue, a chapter, an interlude or an epilogue. A group of modules closed by an interlude or the end of a part forms a part.

## Writing order

1. Modules are written in reading order, because the hook of one chapter is the entry to the next.
2. Exception: a unit that shows something established only in a later module is written after it. For example, a prologue shows a document whose appearance is fixed only by a later chapter; written earlier, it would have to guess. Record such an exception in the unit list.
3. An interlude is written right after the last chapter of its part, because it closes that part's tone.
4. After each part, run the correction loop before the next part starts.

## The cycle of one module

| Step | Content | Who |
|---|---|---|
| 1. Input package | [Unit card](../assets/UNIT_CARD.md), characters' knowledge on that day, the last paragraph of the previous module, canon quotations the scenes need (with chapter numbers), names and their forms, evidence and props in circulation, target length | writer |
| 2. Scene plan | Three to six scenes: place, time, what changes, final image. For key modules, the plan goes to the author before writing | writer, approved by the author |
| 3. Text | First draft, aimed at about 110% of the target length if the project has a minimum | writer |
| 4. Technical check | Length, dates, typography, project limits, work leftovers ([technical check](technical-check.md)). A module with errors does not go to the author | tool or manual list |
| 5. Manual check | Canon, characters' knowledge, point of view, voices, forms of address, real-world details, violence and its consequences, hook, hints of later volumes | writer |
| 6. Report and delivery | Clean text and a separate [report](../assets/UNIT_REPORT.md) | writer |
| 7. Author's decision | "accepted", "accepted with notes" (corrections without changing facts) or "to be rewritten" | author |
| 8. Closing | New facts go into the registers (characters, names, chronology, evidence, knowledge). The tracker gets the status and word count. The accepted text becomes canon for later modules | writer |

**Key modules** are named in the volume plan: the middle of the volume, plot twists, violent scenes, the protagonist's moral decisions, the end of a part. Their scene plan is approved by the author before writing.

A missing decision by the author that a scene needs stops the module before that scene. The author gets 2–3 options with their consequences for later volumes. Independent modules can be written in the meantime.

## Statuses and rules for changes

- Unit statuses: plan, awaiting acceptance, accepted, accepted with notes, to be rewritten, withdrawn. Text not yet accepted by the author is not canon yet, but later modules must not contradict it without a recorded decision.
- **A departure from the card** is allowed if the scene gains from it. Record it in the report and carry it into the card. The plan always describes what was actually written.
- **An accepted module is not changed in passing.** Changing a fact from an accepted module is a separate decision by the author with a list of modules to correct ([series validation](series-validation.md)).
- **Fallback variant:** if a beat depends on a proposal the author has not yet accepted, the report says how it would read without it (for example, one sentence to delete).

## Length

- Words are counted by one described counter, the same for all volumes of a series (for example, runs of characters between whitespace, including headings and date lines). State it in the project rules and in every report.
- If the author set a relation between volumes (e.g. the next volume no shorter than the previous one), derive the unit minimums from it and keep a running total next to the reference volume.
- First drafts usually come out clearly shorter than the target. Plan at about 110% from the start and add missing beats from the card or from open threads; do not add description or paraphrase.
- A unit below the minimum does not go to the author as finished unless the author allowed an exception.
- Stylistic editing shortens the text. If the author forbade shortening, apply "replace and expand": scene content, not filler, takes the place of a removed mannerism.

## The part correction loop

After the module that closes a part:

1. Read the whole part in one go: rhythm, repetition across chapters (the same gesture, comparison, scene entry, ending), length.
2. Compare "who knows what" at the end of the part with the plan.
3. Recompute relative time references ("yesterday", "a week ago", "since Saturday") from the calendar.
4. Compare recurring facts (frequencies, floors, which arm is in a cast, room numbers, who holds a key) by searching the whole part and earlier volumes.
5. Assemble the modules according to the list and, if the project provides for it, make a trial layout.
6. Write a part report with the list of changes to the cards of the following parts.

After the volume, do the same for the whole and then prepare the "state after the volume" ([continuation state](../assets/CONTINUATION_STATE.md)) for the next volume.

The tracker, the cards and the state are the single source of truth about progress. After each part, an assembled working file of the whole is built from the list; check that its length equals the sum of the units.
